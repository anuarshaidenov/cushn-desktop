# CLAUDE.md

Cushn Desktop: a local-first budgeting app on Electron. Public, Apache-2.0 (the name and logo are not: see `TRADEMARKS.md`).

**`ARCHITECTURE.md`** holds the architecture and why each seam exists, the data rules, the behaviour the tests pin, the backup format's compatibility rule, tooling and packaging notes, and the to-do list before shipping. Read it before changing data, IPC, the schema, the backup format, dependencies or packaging.

## Layout and processes

- `src/main`: Electron main process. Owns the window, the SQLite database (`better-sqlite3` + Drizzle) and the IPC handlers. All data access happens here.
- `src/preload`: runs sandboxed (`sandbox: true`, `contextIsolation: true`). Exposes the typed bridge as `window.cushn` via `contextBridge`; it must bundle to a single CommonJS file, so it imports only `electron` and `@shared/*`.
- `src/renderer`: a plain Vite SPA (React 19, TanStack Router with hash history, TanStack Query, Zustand, Tailwind v4, shadcn on Base UI). No SSR, no server functions, no network backend.
- `src/shared`: types and pure code imported by all three. `src/shared/api.ts` holds `cushnContract`, the single declaration of every IPC method; the preload bridge, channel names, `CushnApi` and main's handler map type derive from it. Adding a method: `ARCHITECTURE.md` section 2.

Aliases: `@/*` → `src/renderer/*` (same meaning as in the web app, so copied UI compiles unchanged), `@shared/*` → `src/shared/*`. `src/renderer/routeTree.gen.ts` is generated by the router plugin on `pnpm build`/`pnpm dev`; never hand-edit it.

`scripts/` and the agent skills (`.agents/skills`, `.claude/skills`) are local maintainer tools and gitignored; a script CI runs lives in `.github/scripts/`.

## Data flow

Component → domain hook (`useBudgets()`, `useCreateExpense()`, …) → `cushn.*` (`src/renderer/data/client.ts`, wraps `window.cushn`) → IPC → main-process handler → repository → SQLite.

- Components talk to data only through the domain hooks layer (`src/renderer/data/`). Only that layer knows about `window.cushn` and IPC; `src/renderer/data/layering.node.test.ts` enforces it.
- Failures reach the renderer as `CushnError` (`code`: `NOT_FOUND`, `FORBIDDEN`, …, plus a user-facing `message`); repositories throw it, the IPC envelope carries it.
- Ids are branded per table: `Id<"budgets">` from `@shared/domain`.
- Queries use TanStack `useQuery` / `useInfiniteQuery`; after a mutation, invalidate the affected query keys.
- SQLite lives in the main process only. The renderer and preload never import `better-sqlite3` or Drizzle.

## Conventions

- **Wrap every mutation in TanStack `useMutation`**, and wire the UI to its `mutate` / `isPending`:

  ```ts
  // src/renderer/data/expenses.ts: useMutation + invalidate the "expenses" root
  export function useCreateExpense() {
    return useInvalidatingMutation(cushn.expenses.create, ["expenses"]);
  }
  ```

  Components call `useCreateExpense()` and use `mutate(args, { onSuccess, onError })`. Those per-call callbacks are skipped once the component unmounts (a menu item closing on click, a deleted row). There, call the hook in a parent that stays mounted, or `await mutateAsync(args)` in try/catch. The hook's own invalidation runs either way.
- **One cohesive state object per component**: group related fields into one `useState` object (or `useReducer` for event-driven updates). Independent values (a dialog's open flag vs. a form field) may stay separate. Let children own their own UI state.
- **Lean components**: give each concern one owner, and keep in a component only the state and effects it renders with. When hooks pile up, move them:
  - Effects every row or card would repeat (hotkeys, mutations, hover tracking) register once in the list or its provider, which resolves the target when the event fires.
  - State a component's children share (a menu's pending flag) lives in a wrapper component that provides it through context, so children read it directly.
  - Context reads a component makes together go behind one custom hook.

  `BudgetCard` is the worked example: `BudgetCardContextMenu` (in `BudgetCardActions.tsx`), plus `useSelectableBudget` and `BudgetListHotkeys` (in `BudgetSelection.tsx`).
- **Match the surrounding code style**: naming, file layout, import order and formatting of the neighbouring files.
- **Weigh security by exposure**: harden what ships to users (IPC handlers, the MCP socket, backups); keep dev-mode and maintainer-only tooling simple.

## Code flows public → private only

This repo is public. Some code is ported from a private web app; carry over logic and UI only. Secrets, `.env` values, backend deployment names, URLs and keys from that app stay out of this repo, its commits and its docs. So do its file paths, function names and any description of its weaknesses: comments state this app's own rules, never "unlike the web app, …".

## Verifying work

The user runs the app and checks UI by hand. Verify with these, then hand over a short list of what to look at manually:

- `pnpm typecheck` (node and web tsconfigs)
- `pnpm build`
- `pnpm test` (Vitest, node environment; single file: `pnpm vitest run path/to/file.test.ts`). `*.node.test.ts` under `src/renderer` type-check with the node tsconfig.

Leave `pnpm dev`, `pnpm package`, browsers and screenshots to the user.

## Commits and pull requests

- Open a pull request only when the user asks for one. One request is one PR; split it only when the user asks. Outside contributions: one problem per PR.
- Commit subjects and PR titles are conventional commits in plain language, naming the outcome: `fix(renderer): archiving a budget keeps the grid's scroll position`.
- A PR body states the problem in a sentence or two, then how you fixed it. Commit messages and PR bodies end with the change itself: no model, harness, co-author or "Generated with" lines.

## Documentation

Most code changes need no doc change: agents read the code.

- **`ARCHITECTURE.md`** is the internals doc: decisions and their reasons, constraints that span processes, and traps that are hard to find from the source. Before adding a paragraph, ask what a maintainer would get wrong without it; if reading the code answers that, leave it out. Feature lists, field or method enumerations, control-flow narration, file catalogs and PR summaries belong to the code, types and tests. The glossary defines shared vocabulary, not features.
- A local reason the code can't show goes in a short comment beside that code. Reasoning that crosses processes, or needs context the code can't carry, goes in `ARCHITECTURE.md`, linking to the source rather than copying it.
- When a documented decision or constraint changes, rewrite or remove its text in the same commit, so the doc gives one current account.
- **User-facing text** (`changelog/<version>.md`, which becomes the What's new dialog and the release notes, and `README.md`) speaks in the product's voice about what the user can do, without implementation details or contributor tooling.

## Plans and work tracking

- Plans, research notes and agent scratch files live outside the worktree (`/tmp`), never in a commit.
- Active work is tracked in its GitHub issue; the merged PR or the commit on `main` is the implementation record. When work lands, close or update its issue instead of keeping a checklist in the repo. `ARCHITECTURE.md` section 9 predates this rule and stays until the user moves it; a new to-do goes in an issue (ask before opening one).

## Releasing

macOS only for now: a `v<version>` tag runs `.github/workflows/release.yml`, which signs, notarizes and uploads both archs to a draft GitHub release that the user publishes after testing (`ARCHITECTURE.md` section 8). Never push a release tag or publish a release unless asked.
